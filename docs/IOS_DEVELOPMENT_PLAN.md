# KPKN Fit: iOS Native Migration & Development Plan

### Cardio JSON parity (added 2026-08-19)

Android sessions may now contain the optional `CardioDetails.hiit` object, per-work-block `targetKcal` and `targetDistanceMeters`, and the `CardioType` values `AIR_BIKE`, `SKI_ERG`, `CURVED_TREADMILL` and `SLED`. iOS readers should use defaults when these keys are absent, and iOS writers must preserve unknown cardio keys when round-tripping an Android backup so a future iOS editor does not downgrade a session to legacy steady cardio.

The parity reference for RPE guidance, MET estimates, HIIT/interval expansion and AUGE ring drainage is [CARDIO_3_MODES_CONTRACT.md](CARDIO_3_MODES_CONTRACT.md). This entry documents the future port boundary; it does not claim that the current iOS target already executes cardio.

This document outlines the step-by-step execution plan to build the native iOS version of KPKN Fit using Swift, ensuring 100% parity with the Android architecture.

---

## 🏗️ Phase 1: Foundation & Architecture Setup
*Goal: Establish the skeleton of the app and core UI standards.*

1.  **Xcode Project Configuration:**
    *   Set up the `ios-native/KPKNFit` project using SwiftUI and Swift 6 / iOS 17+ target.
    *   Mirror the Android directory structure: `Presentation/`, `Domain/`, `Data/`, `Services/`.
2.  **Design System Implementation:**
    *   Create `Theme.swift` enforcing the **High-Contrast Dark Mode** (Pitch black background, Neon Yellow, Cyan, Magenta).
    *   Configure global Typography (using custom fonts if applicable).
3.  **Dependency Injection:**
    *   Setup the manual Dependency Injection container at the `App` root level to inject Repositories into ViewModels, avoiding heavyweight frameworks.

---

## 🗄️ Phase 2: Data Layer & Persistence (Local-First)
*Goal: Build the offline database and data mobility systems.*

1.  **Database Engine (`SQLite.swift` or `SwiftData`):**
    *   Define the SQLite schema matching Android's Room tables.
    *   Implement **FTS5 (Full-Text Search)** for the `global_foods` table to ensure instant food queries.
2.  **Static Asset Prepopulation:**
    *   Import and parse the approved `exercise_catalog_v2.json` (parent definitions, explicit configurations, chip axes, exact IDs, and rich metadata), `wikilab/` anatomical JSONs, and `food_data` CSV/TSVs on the first app launch. The retired v1 exercise JSON and alias table are not runtime inputs.
3.  **Cross-Platform JSON Backup:**
    *   Port `DatabaseBackupHelper.kt` to Swift, allowing the iOS app to import the exact JSON backup generated by Android users.

---

## 🧠 Phase 3: Core Domain Engines (The "Brain")
*Goal: Translate the complex math, biomechanics, and AI logic to Swift.*

1.  **Auge Recovery Engine:**
    *   Port the exponential decay formulas for Muscular, CNS, and Spinal batteries.
    *   Port the `DiscomfortCatalog` and mobility prescriptions.
2.  **Biomechanics Engine:**
    *   Port the Stickman anatomical model, lever classifications (1st, 2nd, 3rd class), and anthropometric torque calculations (Femur vs. Torso ratios).
3.  **Training & Session Assistant:**
    *   Port the `SessionAssistantEngine` to handle dynamic rest time reductions and superset suggestions.
    *   Port the Barbell Plate Calculator (linear matching algorithm).
4.  **Nutrition & AI Fallback:**
    *   Port the local heuristic voice parser (`VoiceNutritionRecognizer`).
    *   Implement `ExternalAiService.swift` connecting to Gemini/OpenAI for complex food parsing.

---

## 📱 Phase 4: Presentation Layer (SwiftUI)
*Goal: Build the visual screens following the UDF (Unidirectional Data Flow) pattern.*

1.  **Home Dashboard (`HomeScreen`):**
    *   Implement `MyRingsView.swift` using SwiftUI `Path` and `Canvas` to draw the concentric readiness rings.
    *   Connect `HomeViewModel` to manage daily states and deload warnings.
2.  **Live Workout Tracker (`WorkoutScreen`):**
    *   Build swipeable Set Cards, RPE sliders, and the Barbell Plate Visualizer.
3.  **Nutrition Hub (`NutritionScreen`):**
    *   Build the Macro Rings header and the Voice Dictation Bar.
4.  **Secondary Screens:**
    *   Build `WikiLab` (Anatomical encyclopedia), `SessionEditor` (Drag & drop supersets), and `Settings` (Override sliders).

---

## 🚀 Phase 5: iOS Native Hardware Integrations
*Goal: Leverage exclusive iOS capabilities to match Android's background services.*

1.  **Live Activities & Dynamic Island (`ActivityKit`):**
    *   Replace Android's Foreground Service with a Live Activity that shows the active Rest Timer directly on the Lock Screen and Dynamic Island.
2.  **Voice Recognition (`Speech` framework):**
    *   Implement `SFSpeechRecognizer` for continuous, hands-free workout logging ("Loguea 80 kilos por 8 reps").
3.  **Text-to-Speech & Audio Ducking (`AVFoundation`):**
    *   Use `AVSpeechSynthesizer` for audio cues.
    *   Configure `AVAudioSession` to **Duck** background audio (lower Spotify volume automatically when the app speaks).
4.  **App Widgets (`WidgetKit`):**
    *   Create iOS home screen widgets showing daily macro progress and quick-launch buttons.

## 🧩 Parity note — Cardio intervalos / HIIT (2026-08-18)
- Android (Beta 10+) tiene `CardioDetails.intervalBlocks: List<CardioIntervalBlock>` + `intervalRounds` (JSON embebido con defaults, sin migración Room v23) — ver `data/models/Session.kt:324` doctrina "no requiere migración". Las 6 plantillas HIIT viven como catálogo estático Kotlin (`data/models/CardioHiitTemplates.kt`, patrón `SESSION_TEMPLATES_SYSTEM`, cero Room).
- iOS **no tiene aún** modelo de cardio en `Data/Models/Session.swift` (ni `CardioDetails`/`CardioType`); SessionEditor iOS es placeholder. El JSON nuevo es lenient en lectura (iOS con `JSONDecoder` y defaults ignorará la clave), pero si iOS re-codifica y guarda un `Program` con intervalos, el round-trip pierde los campos → mitigación futura: añadir `Codable` con defaults pasivos en Swift aunque la UI no los consuma.
- Paridad diferida conscientemente en este plan; no bloquea Android. Archivos iOS a tocar eventualmente: `Session.swift`, `WorkoutLog.swift`, `CardioCatalog`, `Domain/Cardio/`, `Presentation/Screens/Workout/CardioLiveCard`, `SessionEditor`.

The recommended approach is to tackle this sequentially: **Data -> Domain -> Presentation -> Native Services**.
