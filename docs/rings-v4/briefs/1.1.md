## El problema (verificado por el orquestador)
`K/screens/auge/AugeViewModel.kt` tiene un `augeWriteMutex` (`:70`, `kotlinx.coroutines.sync.Mutex`, **no reentrante**). `recompute` (`:188-405`) pide ese candado al final (`:395-403`)
cuando `cacheToPersist != null` (primer recálculo del día UTC o cambio de nivel de aviso, ver `LoadAdvisoryEngine.evaluate`, que solo cambia `lastAdvisoryLevelByChannel` y
`lastAdvisoryDay`). Pero cinco funciones públicas ya tienen el candado cuando llaman a `recompute`:

| Función | Toma el candado | Llama a `recompute` |
|---|---|---|
| `saveWellbeing` (`:410`) | `:412` | `:455` |
| `applyManualBatteries` (`:596`) | `:611` | `:697` |
| `dismissAdvisory` (`:1058`) | `:1060` | `:1066` |
| `clearManualBatteryOverrides` (`:1133`) | `:1135` | `:1138` |
| `resetAdaptiveCache` (`:1146`) | `:1148` | `:1151` |

Resultado: en cuanto el primer recálculo del día (o un cambio de aviso) llega a persistir, el `lock()` interno espera para siempre al candado que su propio llamador mantiene; el
`finally { unlock() }` externo no se ejecuta nunca y **todas las escrituras posteriores de AUGE (readiness, cierre, descarte de avisos, `markModelUpdateNoticeShown`…) quedan colgadas en
silencio** hasta reiniciar la app. `recompute` también se llama sin candado desde el colector de `init` (`:167`), `savePostSessionFeedback` (`:466`) y `refresh` (`:473`).

Dos defectos vecinos del mismo código (se arreglan aquí):
1. **Actualización perdida.** `recompute` lee el caché al principio (`:209`) y, al final, guarda `advisoryResult.cache` (una copia **antigua** con los campos de aviso nuevos); y
   `learnFromLatestFinishedLog` (`:840-944`, se ejecuta DENTRO de `recompute` y sin candado) guarda `next` derivado del mismo caché antiguo. Si entre la lectura y el guardado otra
   escritura (p. ej. `learnFromManualAdjustment`, `:834`) cambió τ, el guardado tardío la **pisa**.
2. **Excepciones.** `recompute` no tiene `try/catch`: una excepción mata el colector de `init` o, desde `viewModelScope.launch` sin manejador, tira la app. Y
   `learnFromLatestFinishedLog` usa `runCatching { … }.getOrElse { … }` (`:864-943`), que también traga `CancellationException` (rompe la cancelación estructurada).

## Qué hacer
Archivos permitidos: `K/screens/auge/AugeViewModel.kt` (editar) · `T/screens/auge/AugeWriteMutexTest.kt` (crear) · si de verdad hace falta un seam de pruebas, el cambio
**mínimo** y sin efecto en producción en el propio `AugeViewModel.kt` (p. ej. un constructor secundario `internal` o una fábrica `internal` que reciba las dependencias, con
los singletons actuales como valores por defecto). Nada más.

1. **Reentrada explícita.** Añade a `recompute` (y a `learnFromLatestFinishedLog`) un parámetro `lockHeld: Boolean = false` (nombre libre): los cinco llamadores con candado pasan
   `lockHeld = true`; el colector de `init`, `refresh` y `savePostSessionFeedback` no. Un único ayudante privado, p. ej.
   `private suspend fun <T> withWriteLock(held: Boolean, block: suspend () -> T): T = if (held) block() else augeWriteMutex.withLock { block() }`, y NINGÚN `lock()`/`unlock()` manual
   nuevo (usa `withLock`, que libera siempre).
2. **Persistir fusionando sobre lo último, bajo el candado.** En el punto de `:395-403`: ya con el candado (el propio o el del llamador), vuelve a leer `augeRepo.getAdaptiveCache()`
   y guarda `latest.copy(lastAdvisoryLevelByChannel = …, lastAdvisoryDay = …)` con SOLO esos dos campos tomados de `cacheToPersist`. Mantén la comprobación de generación
   (`generation == recomputeGeneration.get()`) dentro del candado. Igual en `learnFromLatestFinishedLog`: bajo el candado, relee el caché y aplica el resultado del aprendizaje
   (`PerformanceTauLearner.applyToCache(cache = <el caché RELEÍDO>, result, …)` y el sellado `lastPerformanceLearnLogId`) sobre ese caché, no sobre la copia antigua. El resultado
   funcional (qué se aprende, cuándo) NO cambia.
3. **Excepciones.** Envuelve el cuerpo de `recompute` en `try { … } catch (e: CancellationException) { throw e } catch (e: Exception) { … }`: en el `catch`, registra un evento
   diagnóstico (`KpknDiagnosticLogger.event(namespace = "auge", name = "recompute_failed", fields = …)`, como los vecinos), pon `isLoading = false` en el snapshot SIN pisar
   las baterías anteriores y sigue. En `learnFromLatestFinishedLog`, relanza `CancellationException` (no la conviertas en «fallo de aprendizaje»).
4. **No cambies cifras ni el flujo de aprendizaje.** El orden de operaciones dentro de `saveWellbeing`/`applyManualBatteries` queda igual.
5. `refresh` coalescido es **opcional** (no entra en la aceptación): si es trivial y seguro, hazlo; si no, déjalo.
