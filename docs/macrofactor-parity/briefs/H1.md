# H1 · Higiene de datos de nutrición

**Prioridad P0 · esfuerzo S.** Corrige dos riesgos de pérdida de datos/falso éxito (informe §4.9, H-a y H-b) y cierra una higiene de repositorio (H-j). No depende de nada; N2a, N3 y N4 dependen de este paquete.

## Objetivo
1. **H-a — el atajo de creatina y `addLog` no pueden publicar éxito antes de que Room confirme.** Hoy `NutritionViewModel.quickAddCreatine()` → `addLog()` → `NutritionRepository.addNutritionLog()` hace `_nutritionLogs.update { it + log }` y lanza `scope.launch { upsertLog }` sin manejo de error: si Room falla, la comida parece guardada hasta reiniciar. Además captura el objetivo diario con `captureDailyGoalSnapshot(...)` en vez del resolvedor histórico que usa `saveNutritionLog`.
2. **H-b — una fila ilegible no puede vaciar la carga.** Hoy `publishUserState` hace `dao.getAllLogs().map { it.toNutritionLog() }` (y lo mismo con plantillas y planes): una sola fila con JSON roto lanza, cae al `catch` de respaldo y deja VACÍOS registros, plantillas y planes. Debe cargar las filas sanas y poner la ilegible en cuarentena.
3. **H-j — higiene:** el checkout principal tiene APK de terceros sin seguimiento en `artifacts/macrofactor-reference-review-20261017/inputs/`. Añade reglas de ignore para que no puedan entrar por un `git add` masivo.

## Cambio exacto

### H-a
- `NutritionViewModel.addLog(log)` y `quickAddCreatine()` pasan a guardar con `nutritionRepo.saveNutritionLog(log)` (la suspendida y transaccional) dentro de `viewModelScope`. `maybePromptCreatineOnboarding(log)` solo se llama **después** de un guardado confirmado.
- Si el guardado falla: NO se publica el registro, el usuario ve el aviso por la vía que ya existe (`uiMessage` del ViewModel; mira cómo lo usan el borrado y la restauración fallidos) y el atajo no queda en estado de éxito.
- `NutritionRepository.addNutritionLog` no debe seguir publicando antes de persistir. Decide: o la conviertes en un envoltorio `@Deprecated` que delega en `saveNutritionLog` (si hay tests que la usan de forma síncrona, ajusta esos tests), o la retiras si ya no tiene llamadores en producción. Ningún código de producción debe publicar en memoria antes del commit de Room.
- Mantén la API pública del ViewModel que la UI ya consume (nombres de `addLog`, `quickAddCreatine`); si `addLog` pasa a ser asíncrona, actualiza sus llamadores y `NutritionViewModelTest`.

### H-b
- En `NutritionRepository.publishUserState`, decodifica **fila a fila**: registros (`toNutritionLog`), plantillas (`toMealTemplate`) y planes (`toNutritionPlan`). Una fila que lanza se excluye de la lista publicada, se registra con `android.util.Log.w` (id y tipo de fila, sin volcar el contenido) y se anota en un `StateFlow` de solo lectura nuevo (p. ej. `unreadableRows`, con id y tabla) para diagnóstico.
- **La fila ilegible NO se borra ni se sobrescribe** en Room: queda tal cual en la base (cuarentena). Comprueba que ningún camino de escritura la pisa por accidente (p. ej. un «guardar todo» que regrabe la lista publicada).
- El resto del estado (instantáneas, plan activo, catálogo) se publica normalmente aunque haya filas ilegibles. El `catch` de respaldo queda solo para fallos reales de la fase.
- Revisa los otros lectores directos de `toNutritionLog()` (grep) y aplica el mismo criterio si leen la tabla completa en un solo `map` sin protección.

### Test que cambia (decisión D8)
`NutritionRepositoryStartupTest` — `an unreadable user row falls back to the static catalog and still lets the import run` (≈ líneas 209-228) hoy fija que la carga queda vacía. Reescríbelo: con una fila sana y una corrupta en `nutrition_logs`, la sana se carga, la corrupta queda en la base y en `unreadableRows`, el catálogo estático y la importación siguen funcionando.

### H-j
En `.gitignore` de la raíz añade (comentando por qué, en español): `artifacts/macrofactor-reference-review-20261017/inputs/`, `artifacts/**/*.xapk` y `artifacts/**/*.apk`. Comprueba que NO ignoran nada ya rastreado: `git ls-files | grep -E '\.(apk|xapk)$'` debe seguir igual antes y después, y `git check-ignore -v` confirma las rutas nuevas.

## Pruebas obligatorias (nombres orientativos)
- Un fallo de Room al marcar creatina (p. ej. base cerrada o DAO que lanza) no deja el registro publicado ni dispara el onboarding de creatina; el usuario recibe el aviso.
- El guardado correcto del atajo publica el registro con el objetivo histórico resuelto (no el plan activo) y, ya confirmado, puede disparar el onboarding.
- Una fila corrupta entre sanas: las sanas cargan, la corrupta permanece en Room intacta (misma `data`), `unreadableRows` la lista, y el plan activo y las instantáneas se publican.
- Lo mismo para una plantilla y para un plan ilegibles.
- Un reintento tras el fallo no duplica el registro (mismo id → upsert).
