# T3 · Modelo de fuerza único y versionado que usa el RIR

**Prioridad P1 · esfuerzo M.** Informe §4.5 (P1, P8), §5.4 («Qué tomar» y «Validación»; NO uses sus coeficientes), §4.9 (H-f). Depende de **T2** (ya integrado).

## Por qué
KPKN estima el e1RM con **repeticiones solamente** (~35 archivos llaman a `calculateHybrid1RM(peso, reps)` y a variantes Epley/Brzycki/Lander), pero **prescribe** la carga con repeticiones **+ RIR** (`calculateWeightFrom1RMAndIntensity`). Resultado: una serie de 100 × 5 con RIR 2 estima 112,5 kg y luego prescribe 5 @ RIR 2 con ≈ 93,8 kg, un 6 % menos de lo que se acaba de hacer; el sesgo conservador se acumula. Además cada pantalla usa su propia fórmula (Perfil usa Epley, el análisis de programa Brzycki, la sesión y los récords la híbrida), así que el mismo levantamiento muestra e1RM distintos. `Settings.oneRMFormula` (`BRZYCKI | EPLEY | LANDER`) no lo lee nadie.

## Decisiones ya tomadas (README D5)
- **Un solo modelo versionado**: `StrengthModel`, `VERSION = "strength-v1"`.
- La curva de V1 es **la curva híbrida que KPKN ya tiene** (Brzycki hasta 10 repeticiones, Epley de 11 a 20, extrapolación suave por encima), aplicada sobre las **repeticiones efectivas hasta el fallo** `n = reps + RIR`. Estimación y prescripción pasan a ser **inversas exactas**. No introduzcas curvas nuevas ni coeficientes nuevos.
- **Política de RIR ausente = RIR 0** (series históricas sin RIR no cambian de cifra). Fallo / AMRAP / «solo RM» = RIR 0. RPE registrado sin RIR → RIR = (10 − RPE) acotado a ≥ 0 (como ya hace la prescripción). Series saltadas o sin carga/reps válidas no estiman.
- Deja una costura para curvas por región (`StrengthRegion`: tren superior / resto / sin especificar) que en V1 devuelve la misma curva; no inventes parámetros por región (no hay datos propios con que ajustarlos todavía).
- `Settings.oneRMFormula` **no se conecta** (cambiaría cifras de todos): documenta en su KDoc que es heredado y que el modelo es único y versionado. No lo borres.
- Se recalcula la **presentación**; nunca se reescriben registros.

## Cambio exacto

### 1. `domain/performance/StrengthModel.kt` (nuevo, Kotlin puro)
API mínima (puedes añadir sobrecargas; mantén los nombres):
```kotlin
object StrengthModel {
    const val VERSION = "strength-v1"
    /** Reps efectivas hasta el fallo según la política de RIR (arriba). */
    fun effectiveReps(reps: Int, rir: Int? = null, rpe: Double? = null, toFailure: Boolean = false): Int
    fun estimate1RM(weight: Double, reps: Int, rir: Int? = null, rpe: Double? = null, toFailure: Boolean = false,
                    isAmrap: Boolean = false, region: StrengthRegion = StrengthRegion.UNSPECIFIED): Double
    /** Inversa exacta de [estimate1RM] para las mismas repeticiones efectivas. */
    fun weightFor(e1rm: Double, reps: Int, rir: Int? = null, rpe: Double? = null, toFailure: Boolean = false,
                  region: StrengthRegion = StrengthRegion.UNSPECIFIED): Double
    /** Repeticiones hasta el fallo que corresponden a [weight] con ese [e1rm] (para T4; continuo, sin redondear). */
    fun repsToFailureAt(weight: Double, e1rm: Double, region: StrengthRegion = StrengthRegion.UNSPECIFIED): Double
}
enum class StrengthRegion { UNSPECIFIED, UPPER, LOWER }
```
Rangos y redondeos coherentes con los de hoy (mismo tope de 50 repeticiones efectivas, redondeo a 0,1 kg en `estimate1RM` y `weightFor` como hacen las funciones actuales). Documenta en KDoc la política y la versión.

### 3. H-f / P8 — sugerencia contextual de la 2.ª serie
`domain/workout/LoadSuggestionEngine.fatigueFactorForPriorCompletedSets` (1,0 / 0,8 / 0,6 / 0,5) y `screens/workout/WorkoutLoadSuggestionController.determineFatigueFactor` hacen que la sugerencia de la 2.ª serie parta del 80 % de la base aunque el plan pida series rectas con la misma carga. Averigua (código, tests, docs) si es intencional y para qué tipo de serie:
- Si es deliberado solo para series de tipo back-off/drop/etiqueta concreta, consérvalo SOLO para ellas.
- **Criterio de aceptación:** tres series rectas a 100 kg planificadas, sin fallo ni caída de rendimiento: la sugerencia de la 2.ª y la 3.ª es 100 (± el ajuste por rendimiento ya existente), no 80. Con una caída real de repeticiones o un RPE claramente mayor que el planificado, la sugerencia baja como hoy (la señal de fatiga manda; el número de series previas por sí solo no).
- Si tras leer concluyes que es intencional también para series rectas, NO lo cambies: documéntalo en el informe con la evidencia y deja un test que fije el comportamiento.

## Pruebas obligatorias
- **Tabla de oro heredada:** para reps 1..50 y varios pesos, `StrengthModel.estimate1RM(w, r)` (RIR ausente) == `calculateHybrid1RM(w, r)` histórico (guarda los valores esperados en el test; la tabla se calcula una vez con la fórmula actual).
- **Ida y vuelta:** estimar con 100 × 5 @ RIR 2 y prescribir 5 @ RIR 2 devuelve 100 ± el redondeo (0,1 kg). Para una malla de pesos/reps/RIR (RIR 0..4), `weightFor(estimate1RM(w, r, rir), r, rir) ≈ w`.
- **Política:** fallo/AMRAP = RIR 0; RPE 8 ≡ RIR 2; RIR ausente = 0; saltadas/inválidas no estiman; tope de 50 repeticiones efectivas.
- **Monotonía:** más RIR con las mismas reps y peso → e1RM mayor; más peso con las mismas reps → e1RM mayor.
- **Arquitectura:** el test de llamadas prohibidas.
- **H-f:** el criterio de las tres series rectas; el caso con caída de rendimiento; un caso back-off que sigue bajando.
- Regresión: los tests existentes de `domain.calculations`, `domain.workout`, `domain.training`, y los de las pantallas que tocaste siguen verdes (si alguno fijaba la cifra vieja por Epley/Brzycki, actualiza el valor esperado y deja constancia en CAMBIOS_VISIBLES).
