## Availability, stock, and real seams

Current UI routes both `gym` and `home` through five groups—barbell, plates, dumbbells, kettlebells, machines—while `none` skips them (`SetupWizardModels.kt:379–385`; `SetupStepGraph.kt:319–334`). Gym has no “all selected” state/control in the scoped UI; each group starts unanswered and requires actual data or explicit `none` (`SetupWizardModels.kt:882–911`). The controls ask for bar weight, plate kilograms plus count-per-side, dumbbell kilograms, and machine min/max/increment/base (`SetupInventoryControls.kt:537–690, 695–801, 806–917, 1010–1204`); `TrainingOptions.validate` gates finite positive weights/ranges and explicit counts (`TrainingOptions.kt:112–158`). This contradicts the approved availability-only questionnaire.

Those answers are currently actual `EquipmentInventory`, persisted to `Settings.equipmentInventory` at commit (`SetupWizardViewModel.kt:1652–1655`); `Settings.resolvedEquipmentInventory` preserves exact stock and legacy plate counts (`Settings.kt:160–175`). `PlanMaterializer.realizeWarmupLoads` and `WarmupFeasibility` consume those values for reachable warm-up loads; unknown load/material stays pending/UNKNOWN, never phantom kg (`PlanMaterializer.kt:627+`; `WarmupFeasibility.kt:10–20, 114–134, 199–205`). Do not repurpose this stock field as availability. The unresolved seam is where independent availability is durably stored and how it is passed to the shared equipment predicate without making warm-up load resolution believe category selection means actual stock.

There is a single native generator seam: onboarding calls `OnboardingPlanGenerator`, which delegates to `SimpleCyclePersonalizer` (`SetupWizardViewModel.kt:1386–1412`; `OnboardingPlanGenerator.kt:5–35`). Existing approved exercise variants and equipment rules are in `SimpleCyclePersonalizer.equipmentAllows` and `curatedPools` (`:492–507, :676–694`); they include several bodyweight/band/DB alternatives but coverage is uneven (e.g. current calf pool is machine-only, shoulder pool has no bodyweight option, and advanced bodyweight variants are filtered for beginners). Extend these existing pools/recipes and candidate coverage, not a parallel generator. Native generation retains its time/session/weekly-volume checks (`SimpleCyclePersonalizer.kt:187–205, 255–318`) and `ProgramExecutionContract`. Fixed recipes independently pass through `ProgramProtocolEngine` or `ProgramTemplateEngine` into `PlanMaterializer`; hard H1–H11/session bounds remain authoritative (`SessionCompositionPolicy.kt:25–61, 283–321`; `PlanMaterializer.kt:103–110`). Current wizard-supported bounds are 1–6 training days and 20–100 minutes (`SetupStepDefinitions.kt:427–447`); native catalog recipes cover different day ranges (`PersonalizedPlanCatalog.kt:68–78`). Exercise/variant coverage must grow to meet every accepted profile; relaxing these validators is not evidenced as an appropriate fix.

Protocol fidelity is already represented: fixed engines use the authored recipe; materialization keeps `sourceRecipe`, `sourceProtocolId`, and non-native `prescriptionOrigin` (`ProgramProtocolEngine.kt:30–63`; `PlanMaterializer.kt:143–184`). Keep that metadata/prescription path intact and surface a genuinely KPKN-authored executable alternative when a fixed recipe is incompatible. Whether protocol-route UI should interleave the alternative or present a distinct fallback state remains an orchestration decision.
