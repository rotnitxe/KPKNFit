## Findings and exact corrections

### 1. Availability and detailed stock are currently one contract; split the selection path

The current shared method, `TrainingOptions.effectiveEquipment(legacyEquipment)` (`domain/training/TrainingOptions.kt:168-246`), derives selection IDs from `EquipmentInventory` when inventory is non-null. It also emits machine-configuration tokens. That result is used by `SetupWizardViewModel.effectiveEquipmentIds` (`screens/onboarding/SetupWizardViewModel.kt:1238-1239`) for candidate readiness and candidate generation (`:1241-1269`), the fixed-recipe guard (`:1416-1456`), and the native generator (`:1386-1412`). `SimpleCyclePersonalizer.personalize` calls the same helper and then filters catalog configurations (`domain/training/SimpleCyclePersonalizer.kt:135-151, 481-507`).

The requested separation therefore requires changing the *selection API and its callers*, not reusing `inventory` as an availability surrogate:

1. Add a nullable, `@Serializable`, pure-Kotlin `EquipmentAvailability` to `data/models` and a nullable field on `TrainingOptions` (`domain/training/TrainingOptions.kt:48-55`). Keep `inventory` as the existing actual-stock payload.
2. Define an availability-to-canonical-IDs projection and make candidate readiness, native filtering, and fixed-recipe compatibility use that result. Ensure explicit empty availability resolves to `bodyweight` only. Do not infer selected categories or `machine_config:*` from `inventory` in this selection projection.
3. Keep reachable-load resolution on the existing inventory path: `Settings.resolvedEquipmentInventory()` (`data/models/Settings.kt:160-176`), `WorkoutViewModel` (`screens/workout/WorkoutViewModel.kt:6607`), `PlanMaterializer.realizeWarmupLoads`, and `WarmupFeasibility`. Availability must not fill or clear bar weight, plates, counts, dumbbell pairs, kettlebell weights, or machine ranges.
4. Add availability to `SetupInputFootprint` and `SetupWizardDraft.inputFootprint()`/`SetupChangeDetector` (`domain/onboarding/SetupStepGraph.kt:707-783`; `screens/onboarding/SetupWizardModels.kt:388-420`). `trainingKey` already includes the whole `trainingOptions` value (`SetupWizardViewModel.kt:939-951`), but the change-impact footprint does not include availability today. Without that addition, an availability-only change can fail to stale previews and mark `PLAN` pending.

There are only two production call sites of `effectiveEquipment` in the source tree: the onboarding ViewModel and `SimpleCyclePersonalizer`; the latter is reached from the onboarding preview/generator. The newly persisted Settings field would have no existing post-commit selection consumer. `newDraft` reads profile/settings values but does not hydrate equipment (`SetupWizardViewModel.kt:1710-1719`), and the observed workout Settings consumer reads inventory for warm-up loads only. If Settings availability is intended to seed later plan-selection flows, that read path needs to be specified; current code provides none. This does not prevent onboarding preview from using the draft availability, but it is a real boundary on the Settings field’s downstream effect.

### 2. Canonical token contract and machine/support boundary

Existing literal tokens are spread between the `SetupEquipment.catalogId` mapping (`SetupWizardViewModel.kt:1733`), `TrainingOptions` (`:202-325`), `EquipmentInventory.supportEquipment` (`data/models/Settings.kt:387-405`), and fixed-recipe checks (`FixedRecipeEquipmentCompatibility.kt:15-38, 84-139`). The known IDs suitable as category mappings are:

| UI category / capability | Existing canonical ID | Boundary |
|---|---|---|
| Bodyweight | `bodyweight` | Always present in effective selection; empty availability means this only. |
| Barbell | `barbell` | Selection fact only; does not assert bar weight or plates. |
| Dumbbells | `dumbbells` | Does not assert a weight or available pair. |
| Kettlebells | `kettlebell` | Existing ID is emitted from inventory today; no `SetupEquipment` enum member exists. |
| Bands | `band` | Legacy `bands` normalizes to `band`. |
| Pull-up bar | `pull_up_bar` | Separate from generic support. |
| Stable support / rack / bench | `support` | Only the catalogued support-dependent configurations use this token. |
| Ball | `ball` | Separate category/capability. |
| Cardio device | `cardio` | Existing support-equipment ID; separate from outdoor cardio choices. |
| Cable station | `cable` | Explicit multi-exercise station kind. |
| Smith machine | `smith_machine` | Explicit station kind; legacy alias `smith` normalizes to it. |

`SetupEquipment.GYM` currently maps to `general_gym`; that ID is a legacy blanket permission and must **not** be emitted by new availability or the UI-only “Pesos libres” umbrella. There is no `free_weights` token in this training-selection contract. The umbrella must expand to a closed set of actual constituent category IDs (at minimum the supported `barbell`, `dumbbells`, and `kettlebell` categories if those are the intended constituents); do not pass through `general_gym`. `plate` is recognized by `canonicalEquipmentKind`, but the current availability/effective-equipment path does not emit it as a standalone category. `ez_bar`, `trx`, `safety_bar`, `hex_bar`, `t_bar`, `h_bar`, `ghd`, `sliders`, `wrist_roller`, and `ab_wheel` are also recognized kinds, not current onboarding category values; do not silently expand the UI contract to them.

**Machines:** A bare `machine` token does not identify a configuration. The current native filter has a compatibility branch where `inventory == null` plus legacy `machine` can admit every `equipmentId == "machine"` configuration (`SimpleCyclePersonalizer.kt:492-504`); that branch is not safe to reuse for new availability. With declared inventory, the native filter requires `machine_config:<configurationId>`. The fixed-recipe guard independently requires that exact token for `machine` requirements and treats `machine` presence alone as missing (`FixedRecipeEquipmentCompatibility.kt:67-75, 123-139`). `TrainingOptions.effectiveEquipment` documents the same distinction (`:181-192, 214-223`). Thus the category “Máquinas” may record general machine availability but cannot, under current rules, unlock a specific catalog machine configuration. Do not derive or invent `machine_config:*` IDs from the category, row name, or generic machine presence. The currently proven multi-exercise station boundary is explicit `cable` or `smith_machine`; a machine row/name alone does not imply either. Preserve exact-config matching for stock/load calculation where it already exists.

**Support:** `supportDependencyFor` has a closed mapping: pull-up configurations require `pull_up_bar`; inverted row and Nordic curl require `support`; ball hamstring curl requires `ball` (`FixedRecipeEquipmentCompatibility.kt:33-37`). Do not treat generic `support` as any of those separate capabilities, and do not infer support from an equipment name.

### 3. Persistence, legacy repair, and settings-patch requirements

Current durable path is already JSON-based: `SetupWizardDraft.trainingOptions` is serialized as part of the draft (`SetupWizardModels.kt:206-323`; `SetupWizardViewModel.kt:58, 894-896`), and `Settings` is serialized into `SettingsEntity.data` (`data/db/Entities.kt:108-111`). A nullable field with a `null` default on both `TrainingOptions` and `Settings` is compatible with older JSON and requires no Room column migration. Use a serializable closed category representation; preserve null distinctly from a non-null empty category set.

The final settings update must be wired through all three existing patch seams: add `equipmentAvailability: SetupPatchField<EquipmentAvailability?>` to `SetupSettingsPatch`, apply it to the fresh Settings row (`data/onboarding/SetupSettingsPatch.kt:34-83`), and populate it in `SetupWizardViewModel.buildSettingsPatch` (`:1581-1655`). For `null`/unanswered, use `Unchanged`; for explicit none, use `Set(EquipmentAvailability(emptySet()))`, not `Clear` or `Set(null)`. The coordinator applies this patch to the latest Settings within its IO transaction (`SetupPersistence.kt:162-233, 266-295`), so unrelated concurrent Settings remain current. Do not set `equipmentInventory` from availability. Existing stock patching at `SetupWizardViewModel.kt:1652-1654` remains independent and should preserve its current Set/Unchanged behavior. The Settings JSON backup contract (`data/settings/SettingsJsonBackupTest.kt`) should also round-trip the new field and decode older JSON as null.

Draft repair needs more than adding the field:

- Add a productive availability step/control and route it from `SetupStepGraph`/`SetupStepDefinitions`; current graph inserts `INVENTORY_*` from `inventoryGroups` (`SetupStepGraph.kt:38-43, 99-100, 308-334`; `SetupStepDefinitions.kt:37-44, 879-885`). Keep old `SetupStepId.INVENTORY_*` enum values and their serialized data for compatibility.
- `SetupDraftCompatibility.repairStepProgress` currently repairs an out-of-route native cursor using `wizChat.currentQuestionId` rather than the stranded native `currentStepId` (`:132-158`). Once inventory steps leave the productive route, explicitly remap each old `INVENTORY_*` cursor to the new availability step while preserving `trainingOptions.inventory`, `stepSelections`, editor buffers, and all answers. The current fallback can resume elsewhere and is not sufficient for the specified mid-inventory draft.
- Derive a reviewable availability selection only from positive known entries: old explicit category selections and actual nonempty inventory groups/support IDs. Do not turn `SetupEquipment.GYM`/`general_gym` or an environment label alone into every category. If there is no positive evidence, keep null/unanswered; if old user data explicitly means no equipment, convert it to the non-null empty set. Never create numeric stock while deriving.
- On first gym entry, initialize a suggested all-category set once. Do not mark that prefill as a user-declared touch: `mutateDraft(step)` adds the step to `declaredSteps` even when it is a prefill (`SetupWizardViewModel.kt:883-892`), while `SetupWizardDraft.confirmCurrentStep` already records untouched accepted suggestions as `SUGGESTED` (`SetupWizardModels.kt:542-552`). Home must remain null until choice; none must explicitly map to empty availability/bodyweight. Preserve a non-null user-edited selection on gym→home→gym rather than reseeding it.
- Replace `INVENTORY_*` validation/step ownership with availability answered/explicit-none semantics in `SetupWizardModels.kt:849-915`, retain inventory data without exposing new kg/count/range questions, and update the review summary target in `SetupReviewStep.kt:184-221,319+` to summarize availability rather than claim that category selection is inventory stock.

### 4. Body-fat interaction, atomic write, and lifecycle hazards

Current BODY_FAT requires source choice before showing either control, uses a separate compact source row, and routes measured and visual paths independently (`SetupBasicSteps.kt:241-289, 349-405`). A selector drag currently calls `onPosChange` repeatedly and has no completion/cancel callback (`screens/nutrition/WizardPhysiqueFrames.kt:47-81`); `WizardPhysiqueSelector` commits from each position callback and separately writes slider position (`design/WizardPhysiqueSelector.kt:198-208`; `SetupBasicSteps.kt:389-404`). The current callbacks can therefore enqueue multiple `mutateDraft` writes through `SetupWizardViewModel.updateStep`, each serialized but persisted separately (`SetupWizardViewModel.kt:230-231, 883-896`).

Required smallest safe seams:

1. In `WizardPhysiqueFrames.kt:48-81`, expose tap/press completion, drag end, and drag cancel (or an equivalent settled-candidate callback). Current drag handler emits movement only; its separate press handler emits another position but no settlement. Keep movement local to the selector and emit one final candidate on a completed gesture.
2. In `WizardPhysiqueSelector.kt:108-116, 198-208`, keep the latest position/model available while dragging, and distinguish changing the example figure from changing the measured/estimated body-fat source. Figure-sex/model changes must only set `physiqueModel`; they must not write `equationSex`, `bodyFatPercent`, or switch MEASURED to VISUAL_ESTIMATE.
3. In `SetupBasicSteps.kt:241-289, 349-405` and the body-fat reducer (`SetupStepAnswers.kt:143-165, 233-265, 472-507`), render the figure/slider directly with optional exact input and omission. A settled slider gesture should call exactly one atomic `updateStep(BODY_FAT)` that writes model, position, derived percent, source `VISUAL_ESTIMATE`, and capture metadata. Exact input should atomically retain source `MEASURED`. When the active source becomes visual, clear stale measured raw text (`inputTexts[BODY_FAT]`); validation currently gives raw text precedence over the typed percent (`SetupWizardModels.kt:849-862`). Omission must clear percent, captured timestamp, and raw input and prevent an activation observation; the `UNKNOWN` reducer path already does this (`SetupStepAnswers.kt:233-265`), while generic `skipStep` only records an absent answer and does not clear existing fields (`SetupWizardViewModel.kt:238-247`).
4. Do not use the existing `vm.updateStep(BODY_FAT)` for a figure-only switch without changing declaration behavior: it marks BODY_FAT touched through `mutateDraft(step)` (`SetupWizardViewModel.kt:883-892`). A presentation-only figure change must not make the default slider/model a declared body-fat answer. Only a real exact entry, settled estimate, or explicit omission should do so.
5. Make flush part of the navigation contract. `SetupWizardHost` owns Back, Continue, commit, and Save-and-exit calls (`SetupWizardHost.kt:73, 135, 143, 149, 294`); BODY_FAT’s local composable candidate is not available to those calls after unmount. Provide a host/VM-accessible latest candidate and an awaitable flush/settle operation before `goBack`, `submitCurrentStep`, `saveAndExit`, and any commit path. Do not rely on two fire-and-forget calls being ordered: `updateStep` launches a mutex mutation, submit does synchronous validation before its locked revalidation, and `saveAndExit` persists the draft held by the VM (`SetupWizardViewModel.kt:478-539, 688-707`). Flush must complete or be incorporated under the same serialized command boundary before navigation/persistence.

**Cancellation/force-stop contract:** a cancelled gesture must not accidentally lose its latest candidate when cancellation is caused by an explicit Back/Continue/Save-exit; retain it as pending until the explicit flush writes it. A hard force-stop before gesture settlement has no callback opportunity. Under the required write-on-settle/no-per-move-write model, only the last settled value is durable; the unfinished gesture is necessarily discarded. If latest *in-progress* movement must survive force-stop, that requirement conflicts with the one-write-on-settle contract and would require an additional durable staging/journaling decision. This review assumes the stated settled-only durability.

`SetupActivationPayload.bodyObservations` correctly maps MEASURED to measured quality, VISUAL_ESTIMATE to estimated quality, and excludes UNKNOWN/null (`SetupActivationPayload.kt:58-81`). Preserve this. The regression for “measured input then image-sex switch” must assert same measured percent/source and equation sex, and a single measured activation observation. Existing `SetupActivationContractTest.visualEstimateObservationKeepsEstimatedProvenance` is a downstream persistence seam; existing `SetupStepAnswersTest` already covers source switch/UNKNOWN reducer cases and needs a revised direct-control contract.

## Conclusion / blocker

If unfinished drag must survive force-stop, that conflicts with settled-only writes and requires a separate decision.

### AC-1 — category/native, authored fixed recipes, and load boundaries

The decision is coherent as three different gates, but it is **not implemented by simply adding category IDs**:

- **Availability projection:** When `TrainingOptions.availability != null`, `effectiveEquipment` must return the selected category tokens plus `bodyweight` unconditionally. Explicit empty therefore returns exactly `bodyweight`. The closed category-to-token map is `BARBELL→barbell`, `DUMBBELLS→dumbbells`, `KETTLEBELL→kettlebell`, `MACHINES→machine`, `CABLE→cable`, `SMITH_MACHINE→smith_machine`, `BAND→band`, `SUPPORT→support`, `PULL_UP_BAR→pull_up_bar`, `BALL→ball`, and `CARDIO→cardio`. This explicit projection is authoritative: do not union in `general_gym` from legacy `SetupEquipment.GYM`, and do not emit `machine_config:*` from availability or inventory on this path. Existing legacy behavior remains when availability is null.
- **Native KPKN selection:** The approved decision is viable. `SimpleCyclePersonalizer.equipmentAllows` already matches the category-level concept when it receives `machine` and `inventoryDeclared=false`: curated, approved configurations with `profile.equipmentId == "machine"` pass without a configuration token (`SimpleCyclePersonalizer.kt:492-506`). But the caller currently passes `options.inventory != null` as `inventoryDeclared` (`:147-151`), and line 503 rejects every machine configuration lacking `machine_config:<id>` whenever detailed stock exists. Thus a valid explicit `MACHINES` availability plus any non-null inventory is currently rejected. Change that predicate to represent *legacy exact-inventory mode*, not mere inventory presence—for example, enforce exact IDs only when availability is null and the compatibility path is using stock-derived selection. For explicit availability, `MACHINES` must permit categorical native variants whether inventory is null or non-null; do not produce config tokens. `equipmentId == "machine"` still remains required for the machine family.
- **Important shared-helper correction:** `TrainingOptions.effectiveEquipment` currently returns legacy IDs unchanged when inventory is null and replaces them with inventory-derived IDs when inventory is non-null (`TrainingOptions.kt:202-246`). It must branch on non-null availability before either legacy or inventory behavior; otherwise selected categories are ignored when inventory exists, while null availability could preserve a legacy `general_gym` claim. Keep both fallback branches unchanged for old drafts/settings. Also, `SimpleCyclePersonalizer.personalize` calls `options.validate()` before selection (`:128-132`), and `TrainingOptions.validate()` includes stock-honesty reasons (`TrainingOptions.kt:60-82, 120-158`). If availability is to govern exercise selection independently of stock, invalid/unresolved legacy stock must not make an otherwise valid categorical selection fail plan generation; preserve stock honesty for load resolution, but separate that validation from the categorical selection gate.
- **Authored fixed recipes:** Keep `FixedRecipeEquipmentCompatibility` exact. A `machine` requirement is satisfied only by `machine_config:<configurationId>`; bare `machine` is missing (`FixedRecipeEquipmentCompatibility.kt:123-139`). A broad availability category must not manufacture an exact token. Explicit detailed stock remains intact, but under the previously accepted “stock only for reachable-load calculation” boundary it does not become selection evidence either. Consequently, a fixed authored recipe requiring a specific machine may be unavailable even when “Máquinas” is selected; retain the recipe unchanged and offer a genuine KPKN-generated fallback as a separate candidate. The earlier T-001 report identifies that the protocol-only planner currently excludes native entries (`SetupTrainingPlanner.kt:28-51`); this fallback must be added in candidate orchestration later, not by weakening the fixed-recipe guard. Ensure no `general_gym` leaks into explicit availability: the fixed guard has an unconditional `general_gym` success fast-path (`FixedRecipeEquipmentCompatibility.kt:89-93`), which would otherwise bypass its exact machine contract.

### AC-2 — category-only stock honesty and new-draft seeding

**Settings resolution:** Existing `Settings.resolvedEquipmentInventory()` currently turns every `equipmentInventory == null` into `barbellWeight` plus legacy `availablePlates` with unlimited counts (`Settings.kt:160-176`); defaults include a 20 kg bar and a plate list (`:36-46`). Add precedence in this order:

1. If `equipmentInventory != null`, return that explicit inventory (with existing sanitization) unchanged by availability—even an explicit empty inventory stays empty.
2. Otherwise, if `equipmentAvailability != null`, return an empty/unknown `EquipmentInventory` with no bar, plates, pairs, kettlebells, or machine ranges. This must not mutate `barbellWeight` or `availablePlates` on Settings.
3. Otherwise, preserve the current legacy fallback exactly.

The existing load consumer is `WorkoutViewModel` (`WorkoutViewModel.kt:6607`, as traced in T-003 v1), which passes `resolvedEquipmentInventory()` into reachable-load resolution. No other resolver behavior should be changed: availability controls exercise categories, while this Settings path controls load reachability. An empty resolved inventory must leave barbell warm-up loads pending/unrealized rather than calling a 20 kg/default-plate fallback.

**Draft seeding:** Seed stored availability only in `SetupWizardViewModel.newDraft` (`:1710-1719`), by initializing the draft’s `trainingOptions.availability` from `settings.equipmentAvailability` when non-null. The existing initialize flow chooses the restored JSON draft instead of calling `newDraft`; do not merge Settings availability over a restored/resumed draft, including a deliberately null value. The new draft’s `declaredSteps` remains empty: this is a suggestion/prefill, not a new declaration. `confirmCurrentStep` already records an untouched accepted suggestion as `SUGGESTED`; preserve that distinction.
